# 2026-10-26: slice 16, db-sync 2.4.0, patch 0001 retired, checkout layout migration

*Written by Claude (coding session) after implementing the brief
`2026-10-21d`. Upstream released db-sync 2.4.0 on 2026-10-19 with our
#187 in revised form; this slice moves the image to it. Nothing here has
run against Docker or a database: 178 tests pass on the development
machine, the db-tagged ones and the field items below are for
gis-ubuntu.*

## What changed upstream, and what it meant for the manager

Read first: `git log 2.3.0..2.4.0` (44 commits) and the diffs of
`dbsync.py`, `dbsync_daemon.py`, `config.py`, `requirements.txt`. The
image tag `lutraconsulting/mergin-db-sync:2.4.0` exists on Docker Hub
(published 2026-10-19; `latest` points at it).

1. **#187 revised** (`_get_work_dir()`): checkout per connection at
   `<working_dir>/<project name>-<modified schema>`. Patch 0001 assumed
   `<project name>/<modified schema>`. The manager now has one place
   that knows the layout, `supervisor/layout.py`; `SyncConnection.
   checkout_dir`, `check.local_version_of`'s caller, `verify.py` and
   the config renderer go through it. `working_dir` itself is unchanged
   (`/data/projects/<id>/work`), db-sync adds the subdirectory.
2. **#128 sparse checkout**: `download_project(..., include=[sync_file])`
   with mergin-client 0.15.0, which also writes
   `.mergin/file_filter.json`. `.mergin/mergin.json` still carries
   `version`, so `local_version_of` is unchanged (test
   `tests_layout.test_local_version_of_a_sparse_checkout`). A checkout
   is one GeoPackage plus `.mergin/`.
3. **#190 auth token store**: `<working_dir>/.mergin_auth.json`, mode
   0600, reused across restarts and `--force-init`. For the manager it
   is one more secret under the project's work dir: documented in the
   README's file table, `docs/backup.md` (not dumped, nothing to restore)
   and CLAUDE.md. Nothing in the manager lists or copies the work dir;
   hooks get `DBSYNC_WORK_DIR` and must not print it. Remove deletes the
   work dir as before.
4. **Not in the brief: in-process retries.** 2.4.0's `run_daemon()` no
   longer exits on a failed login or init. It retries inside the process
   with backoff (up to 10 min, up to 1 h for logins) and exits only after
   `daemon.max_failed_retries` consecutive failures, default 10, about
   an hour. That would have hidden every deterministic exit from
   `exits.classify_exit` (slice 14) for an hour: `checkout_inconsistent`
   would show as a running daemon logging the same error. The generated
   config therefore sets `max_failed_retries: 1` (one retry after
   `sleep_time`, then exit; 0 would mean never). Sync errors after a
   successful start are retried in-process indefinitely as they were in
   2.3.0, now with backoff up to 10 min instead of every `sleep_time`.
   Unexpected (non-DbSyncError) exceptions are now caught and retried
   once too, instead of a traceback and immediate exit.
5. **#142 project-id check**: init now raises "Mergin Maps project ID
   doesn't match ... stored in the database" when the config points at
   another project than the schemas were created from. The text ends
   with `--force-init`, which `exits.py` already maps to
   `checkout_inconsistent` (deterministic, Re-init). The advice text
   says "checkout and database no longer agree", which is close enough;
   a dedicated condition can come if it is ever seen.
6. `_set_db_project_comment` now always stores `project_id` as a string
   in the base schema comment. `dbinspect.base_schema_comments` reads
   the comment as JSON and ignores unknown keys; nothing to change.

## Patch 0002 on 2.4.0

Rebased by regenerating from the 2.4.0 sources (`patches/upstream/` is
now 2.4.0, `*.patched` the result). The daemon part moved into
`run_daemon()`: the stop check at the top of the cycle, between pull and
push, and `sleep_unless_stopped(wait_time)` instead of
`time.sleep(wait_time)`, which also covers the new retry waits. The exit
between pull and push is a `SystemExit` raised inside 2.4.0's
`try/except Exception`; it passes through because `SystemExit` is a
`BaseException`, and `tests_patches` has a test for exactly that. The
`dbsync.py` part applied without change.

`patches/UPSTREAM.md` holds the issue text, the PR text and the
`test/test_daemon.py` change (their `run_daemon` fixture must mock
`sleep_unless_stopped` instead of `time.sleep`). There is no GitHub CLI
on the development machine, so filing is Nicklas's step; the README
table gets the links afterwards.

## Migration of existing checkouts (C)

Re-download, as the brief chose. The rename alternative was not needed:
db-sync's own init already handles "schemas exist, no checkout" by
downloading at the database's version and comparing base with the
GeoPackage, and a sparse checkout is what we want anyway.

Without the manager doing anything, the first start after the upgrade
would have done that re-download for every project at once, because
`_get_work_dir()` points at a directory that does not exist. So:

- `layout.needs_migration(work_dir, mergin_project)`: the 2.3.0 tree
  `work/<project name>/` exists and no marker `work/.layout-v2` does. A
  project added after the upgrade never has the tree; one that never
  started has no tree. `Supervisor._start` refuses such a project with
  process state `blocked` and one warning event ("run 'Migrate
  checkouts' ..."), tested through `_reconcile`.
- The `migrate` operation: `wait_turn → block → stop_child →
  remove_old_checkout → redownload`. `wait_turn` waits while another
  migrate operation is running past that step (a registry query, so it
  survives a supervisor restart); operations are now advanced in pk
  order. `remove_old_checkout` removes the tree and writes the marker.
  `redownload` starts the daemon under the operation (the operation owns
  the project, `_reconcile` does not run for it) and waits until every
  connection's checkout has `.mergin/mergin.json`, which mergin-client
  writes when a download has finished; then one event "checkouts
  downloaded in N s in the db-sync 2.4.0 layout (...)". A daemon that
  exits meanwhile fails the step after `_handle_exit` has recorded the
  exit (so "stopped cleanly" and crash classification still appear);
  retry starts it again. After 30 min without the download finishing
  the step fails and the daemon keeps running; retry keeps waiting. A
  paused project gets the tree removed and the marker, and downloads
  when resumed.
- Requested from the Projects page (notice "Checkout migration pending"
  with the list and a button for operators) or `manage.py
  migrate_checkouts [--list]`; one operation per project, projects with
  an open operation are listed as "not touched".
- Kind `migrate` needed `Operation.kind` widened to 10 characters
  (migration 0016). `docs/api.md` lists it.
