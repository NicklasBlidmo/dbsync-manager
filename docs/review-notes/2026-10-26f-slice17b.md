## Why the direction was wrong

Slice 17a read geodiff's `conflictToJSON`: `old` = "theirs", `new` =
"ours", and took "theirs" for the server and "ours" for the database,
which is right, and then assumed the rebase keeps "theirs". It does
not: the rebase rewrites our changes on top of theirs and db-sync pushes
the result, so in a same-column conflict the database's value is what
both sides end up with. geodiff's `old`/`new` naming describes the
rewrite (the field's value is the "old" one that gets replaced), not who
wins. CLAUDE.md now says so, because the naming invites the same mistake
again.

## Fix 1: text

`conflicts.Conflict.columns` carries `field` and `database`;
`deleted_in_field` replaces `deleted_on_server`. The event now reads, for
the test file of `tests_conflicts`:

    rebase: 1 field value in linjer (column #1) overwritten by the database value, fid 2;
    2 field values in punkter (namn, typ) overwritten by the database values, fid 17, 41;
    1 database update of row deleted in the field in punkter dropped with the row, fid 50.
    The overwritten field values are in conflicts/20261027T101502-1-punkter.gpkg.json

The API's per-table entry gains `deleted_in_field` and `fids_deleted`;
`deleted_on_server` stays with the same number because v1 never removes
a field, and `docs/api.md` says it is the first day's name.

## Fix 3: the case nobody recorded

Patch `0003`, in db-sync's `pull()` right before `_geodiff_rebase`:
`_report_lost_field_updates(tmp_base2our, tmp_base2their)` lists both
changesets with the existing `_geodiff_list_changes_details` (`geodiff
as-json`), matches delete entries of ours against update entries of
theirs by the row's key (the columns an update carries only an `old`
value for, which is how geodiff's JSON marks the primary key; a delete
carries every `old`), and logs one WARNING per lost update:

    field update lost: table punkter row (column 0 = 631) was deleted in the database;
    the update from Mergin Maps (column 3: 'ny text') is dropped with the row

A geodiff failure inside it is logged and never breaks the pull. Doing
it inside db-sync, per connection, is why it is a patch and not a
supervisor step: the supervisor sees the temp changesets only after the
whole cycle, and with several connections per project the per-project
file names would have hidden all but the last.

The note said "no new geodiff call"; there are two `as-json` calls per
rebasing pull. They cost milliseconds and run only when a rebase is
about to happen.

logtail: a WARNING record whose text starts with `field update lost:` is
a `warning` event; every other WARNING line stays an error event as
before (2.4.0's "auth token was rejected" among them, unchanged).

`tests_patches` applies 0002 and 0003 as the Dockerfile does, and tests
`_lost_field_updates` and the report on the loaded patched module.
